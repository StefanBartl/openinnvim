### B-F-01: INSTANCE_PICK='ask': chooser dialog is invisible when started through the hidden VBS chain; ShowDialog() blocks forever

- Schwere: **high**, Art: bug, Ort: `E:\repos\openinnvim\open-in-nvim.lib.ps1:414`

**Behauptung**

> The VBS starts powershell.exe with WScript.Shell.Run(cmd, 0, False) (SW_HIDE in STARTUPINFO). Windows applies that nCmdShow to the FIRST ShowWindow call of the process, which is the one WinForms makes for the chooser form. The form therefore never gets WS_VISIBLE: it exists, is even the foreground window, but is not on screen. Show-NvimChooser then waits in $form.ShowDialog() (line 430) until the user presses Enter/Escape in a window they cannot see, i.e. forever: nothing is opened and every click leaves a hidden powershell.exe behind. The suite only constructs the form and invokes OnDoubleClick by reflection (run-tests.ps1:152-160), so it cannot catch this.

**Beleg**

> Probe chooser-hidden2.ps1 started by a VBS copy of the real Run call (sh.Run cmd, 0, False), building the form with the lib's New-NvimChooserForm and self-closing after 1.2 s: 'style: 0x06cf0000 WS_VISIBLE=False / IsWindowVisible: False / foreground: True / window at form centre: hwnd=40831680 root=4982830 ownerPid=24256 isOurForm=False myPid=48436'. Same probe with one extra ShowWindow(hwnd, 5) in Add_Shown: 'style: 0x16cf0000 WS_VISIBLE=True / IsWindowVisible: True / window at form centre: ... isOurForm=True'. Lib line 414: $form.Add_Shown({ $form.Activate(); $list.Focus() }.GetNewClosure()); line 430: [void]$form.ShowDialog(). VBS line 24: sh.Run cmd, 0, False.

**Reproduktion**

> Reproduced in scratch: scratchpad\oin-review\chooser-hidden\hidden2.vbs + chooser-hidden2.ps1 (OIN_PROBE_MODE=plain). Real-world: set INSTANCE_PICK = 'ask', have two instances with a UI running, right-click a file -> 'Open with Neovim (current instance)': no dialog appears, nothing opens, Get-Process powershell shows a lingering hidden process.

**Vorgeschlagene Behebung**

> In New-NvimChooserForm make a second, explicit ShowWindow call once the handle exists (ShowWindow is already declared in OpenInNvim.Win32, lib line 494):
> $form.Add_Shown({
>   Initialize-OpenInNvimWin32
>   [void][OpenInNvim.Win32]::ShowWindow($form.Handle, 5)   # SW_SHOW: the VBS starts us SW_HIDE and Windows applies that to the first ShowWindow call only
>   $form.Activate(); $list.Focus()
> }.GetNewClosure())
> Verified with the probe above (WS_VISIBLE=True, form found at its own centre). Optionally add a test that starts the chooser through wscript hidden and asserts IsWindowVisible, and a safety timer so ShowDialog can never block forever.

### B-F-03: WScript.Shell.Run expands %NAME% inside the path before PowerShell sees it (documented '%TEMP% folder is used as typed' is false through the real chain)

- Schwere: **medium**, Art: bug, Ort: `E:\repos\openinnvim\open-in-nvim-current.vbs:24`

**Behauptung**

> Both VBS files build one command string and hand it to WshShell.Run, which expands environment-variable references in that string. A path containing a %NAME% that is an existing variable (folder '%TEMP%x', file '%USERNAME%.txt', ...) reaches the .ps1 already expanded, so the launcher's own guard (only expand when the path as given does not exist, open-in-nvim-current.ps1:161-164) and the suite's check 'a folder named %TEMP%x is not environment-expanded' (run-tests.ps1:257-260, which calls the .ps1 directly) never see the original. Same in open-in-nvim.vbs:24. docs/troubleshooting.md:73 and docs/FEATURES/NEW-INSTANCE.md:16 promise the opposite.

**Beleg**

> Explorer-style call wscript.exe //nologo "<vbs>" "C:\%TEMP%x\f.txt" against the unmodified open-in-nvim-current.vbs and a stub .ps1 dumping $args: 'percent_env DIFF sent=[C:\%TEMP%x\f.txt] count=1 got=[C:\C:\Users\bartl\AppData\Local\Tempx\f.txt]'. A VBS that writes WScript.Arguments(0) directly shows wscript itself received it unexpanded: 'sent=[C:\%TEMP%x\f.txt] wscript got: count=1 [C:\%TEMP%x\f.txt]' - the expansion happens in sh.Run. Non-variable percent names pass: 'percent_noenv OK [C:\100%done%x\f.txt]', 'percent_single OK [C:\50% off.txt]'.

**Reproduktion**

> Reproduced (scratchpad\oin-review\vbs-boundary2.ps1). Real-world: a folder literally named %TEMP%x (or any %VAR% whose VAR exists) -> the launcher opens/creates a path under the expanded value instead.

**Vorgeschlagene Behebung**

> Hand the path over in the process environment instead of the command line (Run does not expand environment values); this also removes the whole quoting block. Verified in scratch (envfix.vbs): %TEMP%x, trailing backslash, drive root and unicode all arrive unchanged.
> VBS:
>   Set env = sh.Environment("PROCESS")
>   If WScript.Arguments.Count > 0 Then env("OPEN_IN_NVIM_TARGET") = WScript.Arguments(0)
>   sh.Run <powershell ... -File "...\open-in-nvim-current.ps1">, 0, False
> .ps1 (both launchers):
>   $TargetPath = if ($env:OPEN_IN_NVIM_TARGET) { $env:OPEN_IN_NVIM_TARGET } elseif ($args.Count -gt 0) { $args[0] } else { $PWD.Path }
> Add a VBS-chain test case with a %TEMP%x folder to run-tests.ps1 (the existing one bypasses the VBS).

### B-F-05: The stable pipe and NVIM_SERVER candidates get none of the discovery checks (UI, nvim.exe, own session): a headless owner, or a pipe squatted by another local user, silently receives the file

- Schwere: **medium**, Art: security, Ort: `E:\repos\openinnvim\open-in-nvim-current.ps1:203`

**Behauptung**

> Get-NvimInstances only accepts a pipe whose PID is nvim.exe in the launcher's logon session with len(nvim_list_uis())>0 (lib 76-87). The per-user name is accepted on mere existence (Test-NvimPipe, line 203) and NVIM_SERVER unconditionally (196-198), then Invoke-NvimOpen sends the path and returns success (:drop works headless). lib.nvim's rpc_pipe.setup calls serverstart(\\.\pipe\nvim-<USERNAME>) in every nvim with the user's config that has no NVIM_LISTEN_ADDRESS and is not a detected test env (rpc_pipe.lua:33-35, 65-68), so a plain 'nvim --headless ...' started from a shell before the TUI owns the name; the click then 'succeeds' with nothing visible, and because the name is taken the real TUI never gets it. Pipe names are global on the machine, so another local user (or any process) can also create \\.\pipe\nvim-<victim> first and receive every clicked path (information leak + the file never opens), while the headless-only check is bypassed.

**Beleg**

> Experiment E4: fixture 'headless' instance ran serverstart('\\.\pipe\nvim-oin_review_35f1e4') -> 'uis=0 exists=True'; launcher copy with the OnlyPids gating of the stable pipe removed, USERNAME=oin_review_35f1e4: 'dry run exit=0: candidate: \\.\pipe\nvim-oin_review_35f1e4 / candidate: \\.\pipe\nvim.59820.0', 'real run exit=0 in 1012 ms', 'headless buffers: [...\headless test.txt]', 'gui2 (newest, has a UI) buffers: []'. docs/architecture.md:54-55 claims 'a click never sends a file into another logged-in user's editor'.

**Vorgeschlagene Behebung**

### B-F-06: tests/run-tests.ps1 aborts at 99/104 with CommandNotFound 'Get-FileHash' whenever Windows PowerShell 5.1 inherits the PSModulePath of a PowerShell 7 ancestor

- Schwere: **medium**, Art: compat, Ort: `E:\repos\openinnvim\tests\run-tests.ps1:417`

**Behauptung**

> Get-FileHash is a function from Microsoft.PowerShell.Utility.psm1 (5.1). When powershell.exe inherits pwsh 7's PSModulePath (c:\program files\powershell\7\Modules before C:\Windows\system32\WindowsPowerShell\v1.0\Modules), 5.1 resolves the module name to pwsh's manifest first, the module shows 0 exported functions and Get-FileHash does not exist. pwsh special-cases only a direct '& powershell.exe' child (clean path); any other route - cmd.exe, Process.Start, Neovim's :!/jobstart inside an nvim started from pwsh 7, CI steps, this review harness - passes the pwsh path on. The suite then throws ($ErrorActionPreference='Stop') before the in-place and dry-run checks and before the 'passed:' summary; exit code 1. The launchers themselves are not affected (Explorer's environment is the clean machine value; Get-CimInstance is still found in the inherited environment).

**Beleg**

> Three runs (two of the original, one instrumented copy): 'ok lines: 99 / FAIL lines: 0 / summary line: (none)' then 'Get-FileHash : Die Benennung ... nicht ... erkannt ... run-tests.ps1:417'. Instrumented copy, probe at start of the run: 'Get-FileHash=MISSING utilModuleLoaded=yes exportedFunctions=0 listAvailable=2', '[probe] PSModulePath=C:\Users\bartl\Documents\PowerShell\Modules;C:\Program Files\PowerShell\Modules;c:\program files\powershell\7\Modules;C:\Program Files\WindowsPowerShell\Modules;C:\Windows\system32\WindowsPowerShell\v1.0\Modules'. Contrast: '& powershell.exe -NoProfile -Command $env:PSModulePath' from pwsh 7.6.6 prints the clean 3-entry path and Get-FileHash is 'FOUND (Function, Microsoft.PowerShell.Utility)'; 'cmd.exe /c echo %PSModulePath%' prints the pwsh path and in that child 'MISSING Get-FileHash', 'MISSING Import-PowerShellDataFile', 'found Get-CimInstance'. Machine PSModulePath (persistent) is clean.

**Reproduktion**

> Reproduced: powershell.exe -NoProfile -ExecutionPolicy Bypass -File E:\repos\openinnvim\tests\run-tests.ps1 started via [Diagnostics.Process]::Start from pwsh 7 (or via cmd.exe /c from pwsh 7). From a pwsh 7 prompt with '& powershell.exe ...' it would not trigger.

**Vorgeschlagene Behebung**

> Do not depend on the psm1 function in the suite; compare bytes directly, e.g.
> $cfgBefore = [IO.File]::ReadAllBytes($cfgPath)
> ... Assert-That '...' ([Linq.Enumerable]::SequenceEqual($cfgBefore, [IO.File]::ReadAllBytes($cfgPath)))
> (or [BitConverter]::ToString([Security.Cryptography.SHA256]::Create().ComputeHash($bytes))). Also add a hint in docs/CONTRIBUTING.md that the suite must be started as '& powershell.exe ...' from pwsh or from cmd with a clean PSModulePath; optionally reset $env:PSModulePath to the 5.1 default at the top of run-tests.ps1 and in the launcher scripts.

### P-PERF-1: Unreachable TCP NVIM_SERVER costs 5.7 s per click and starts a hidden full editor with the user's config

- Schwere: **high**, Art: performance, Ort: `E:\repos\openinnvim\open-in-nvim-current.ps1:273`

**Behauptung**

> For a TCP NVIM_SERVER nobody listens on, `nvim --server <addr> --remote <file>` does not fail fast: Neovim prints E247 and falls back to "Editing locally", i.e. it starts a complete TUI session in the hidden console, loads the user's init.lua, opens the clicked file there, and blocks until Invoke-Bounded kills it with taskkill /F after 5000 ms (which also leaves a stale swap file for that file). ### P-PERF-2: An open that takes longer than 3 s is treated as a refusal: 3.6 s wait and the file is opened in a second instance as well

- Schwere: **high**, Art: performance, Ort: `E:\repos\openinnvim\open-in-nvim-current.ps1:296`

- Schwere: **medium**, Art: performance, Ort: `E:\repos\openinnvim\open-in-nvim.lib.ps1:76`

**Behauptung**

> Get-NvimInstances performs one RPC per nvim.exe pipe of the session, one after the other, each with its own 500 ms limit, and only afterwards Select-NvimInstance orders the result. Responsive helpers are cheap (3-4 ms warm, 5-10 ms in the fresh process), but every hung or main-thread-busy instance adds a full 500 ms, and the cost grows linearly with the number of instances (the `-l` fixture host owns a pipe too and is probed in real use; there is no command-line filter by design). With INSTANCE_PICK newest/oldest the launcher could stop at the first instance with a UI in start-time order.

**Beleg**

> profile.ps1: `Get-NvimInstances -OnlyPids gui2 (1 pipe) med=26.4`, `gui1,gui2 (2 pipes) med=29.8`, `all 4 own (4 pipes probed) med=35.7`; `Get-NvimInstances with gui1 hung: 542 ms`; `UI check headless helper med=4.3`, `embed+headless helper med=3.5`. measure.ps1: `b4 4 own pipes 573` vs `b 2 instances 546` (+27 ms for two helpers in a fresh process). extra.ps1 E4: `fixture host pid=64932 pipes=1 \\.\pipe\nvim.64932.0`, `UI check on the -l host: [0] in 5 ms`; `all nvim.* pipes on the machine now: 6`. Code: open-in-nvim.lib.ps1:76-87 (foreach with Invoke-NvimEval per entry), :31 entries sorted by Pid (the fixture's gui1 had the higher PID, so pipe order is unrelated to pick order); open-in-nvim-current.ps1:215 Select after the full scan.

**Reproduktion**

> Fire a 4 s busy loop into one own instance (`nvim_exec_lua` with `while (vim.uv.hrtime()-t) < 4e9 do end`, 60 ms request timeout), then time `Get-NvimInstances -OnlyPids <busy>,<other>`: ~540 ms, result contains only the other one.

**Vorgeschlagene Behebung**

> (a) For newest/oldest: build the candidate list from the pipe entries plus Process.StartTime (free), sort, then probe lazily and stop at the first instance with a UI. (b) For 'ask' (needs all): connect and write to all candidates first, then wait with one shared deadline, e.g. collect the ReadAsync tasks and `[System.Threading.Tasks.Task]::WaitAll($tasks, 500)`, then decode whatever arrived. Expected: K hung instances 500*K -> <=500 ms total; typical 2-4 instances -10..-30 ms.

### P-PERF-8: FOCUS_TERMINAL costs ~400 ms per click (CIM table 190-300 ms + Add-Type compile 170-190 ms in every fresh process), not a "one-off compile"

- Schwere: **low**, Art: performance, Ort: `E:\repos\openinnvim\open-in-nvim.lib.ps1:537`

**Behauptung**

> Set-NvimInstanceFocus reads the whole Win32_Process table through CIM (190-300 ms, the filter makes no difference) and compiles the P/Invoke type with Add-Type; because every click is a new powershell.exe, the compile is paid every time (167-190 ms), plus Get-Process per ancestor. The config comment and docs/configuration.md call this a one-off compile. Opt-in, so low severity, but the measured 0.4 s per click doubles the launcher's own cost.

**Beleg**

> profile.ps1: `Get-CimInstance Win32_Process -Property ProcessId,ParentProcessId (all) med=192.4 first=296.8`, `-Filter Name=nvim.exe med=188.9`, `WHERE ProcessId=<gui1> med=191.3`; `Add-Type OpenInNvim.Win32 (one-off compile) first=132.7` (warm process). baselines.ps1 fresh processes: `addtype-compile-ms=190 || 179 || 167`; `Add-Type -Path cached.dll: addtype-path-ms=79 || 74 || 75`; `Get-WmiObject (all) med=226.9`, `[wmisearcher] one hop med=195.5`. Code: open-in-nvim.lib.ps1:492 Add-Type -MemberDefinition, :537 Get-CimInstance, :542 Get-Process per hop; open-in-nvim.config.ps1:34-36 and docs/configuration.md:77-78 ("a one-off compile").

**Reproduktion**

> Set FOCUS_TERMINAL = $true in a scratch config copy and time the launcher; or run the two baselines.ps1 fresh-process Add-Type scenarios.

**Vorgeschlagene Behebung**

> Add `NtQueryInformationProcess` (ntdll, ProcessBasicInformation -> InheritedFromUniqueProcessId) to the same Add-Type block and walk the parents per hop in microseconds instead of fetching the CIM table (-190..-300 ms); compile once at install time with `Add-Type ... -OutputAssembly <InstallDir>\OpenInNvim.Win32.dll` and `Add-Type -Path` at run time (-100 ms). For WezTerm a more precise and cheaper route exists: `nvim_eval('$WEZTERM_PANE')` in the instance and `wezterm cli activate-pane --pane-id <id>`, which also picks the right window. Expected: ~400 -> ~100 ms. Fix the wording in open-in-nvim.config.ps1:35 and docs/configuration.md:77.
